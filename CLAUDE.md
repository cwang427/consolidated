# ConsoliDated

A private two-person date-journal web app: shared date-idea list (a wishlist, deliberately **not** linked to logged dates — a real date usually spans several activities), journal of logged dates (per-partner reflections + photos), calendar/album history, Leaflet maps showing both home bases and multi-stop day routes.

## Architecture (deliberate constraints — keep them)

- **Single file.** The entire app is `index.html` — inline CSS + vanilla JS, no build step, no framework. Keep it that way unless the user asks otherwise.
- **Hosting:** GitHub Pages from this repo's `main` root. Deploy = commit + push; live ~1 min later.
- **Bump `<meta name="build">` in every commit that ships.** It's the app's version stamp and there is no build step to generate it, so it only stays honest if each change edits it by hand — format `YYYY-MM-DD.n`, `n` counting that day's deploys. Settings → Version shows it and re-fetches the deployed `index.html` (`checkBuild()`, `cache:'reload'` so the stored copy is replaced and the Reload button actually gets the new file) to say whether an installed PWA is running the latest. A stale stamp makes that check quietly lie, which is worse than not having it.
- **Backend:** Firebase Firestore only, **Spark (free) plan — a hard project constraint**. No Cloud Storage (requires Blaze/credit card), no phone auth (same reason), no paid anything.
- **Video clips:** a picked video never reaches Firestore. It is decoded locally, the chosen window (up to 3s) is redrawn through a canvas and re-encoded with MediaRecorder (`CLIP_MAX_MS/CLIP_MIN_MS/CLIP_FPS/CLIP_DIM` = 3s max / 0.3s min / 12fps / 1080p cap; `clipWindow()` clamps the two trim handles, `clipBps()` scales the bitrate target by length so any duration still fits one doc), and only that silent loop is stored — as a normal `photos` row with `kind:'clip'`, so ordering, covers, arrange mode and trash all work unchanged. Some encoders accept a format then emit **zero bytes** (Chromium's mp4 encoder does this at 1080p under load), which would save a broken clip, so every recording is validated against `MIN_CLIP` and `compressClip` steps down through format→resolution→bitrate, memoising the combo that worked in `clipEncoder`.
- **Photos** live *in Firestore* as base64 JPEG data URLs: client-side compression to ≤1600px / <~930K chars (Firestore 1MiB doc limit). Collections: `photos` (thumbnail + meta) and `photoFulls` (full image), split so list views only load thumbs. Opening a photo therefore costs a document read, with the thumbnail standing in meanwhile — so the viewer caches fulls in `fullCache`, a module-level LRU **keyed by `fullId`** and capped at `FULL_KEEP`. Keying by id rather than hanging the data off the photo object is the point: the `photos` snapshot handler rebuilds `S.photos` from scratch, which silently discarded a per-object cache and made every reopen re-download. `loadFull()` reads the **on-disk copy first** (`get({source:'cache'})`, backed by `enablePersistence()` — free of both the network and the read quota, and the reason a relaunch no longer re-downloads everything), then falls back to the server through `LOAD_TRIES`: a Firestore `get()` has no timeout of its own, so on a channel that has died without the SDK noticing — an iOS PWA resumed from background — it hangs forever. Each attempt is capped and re-issued (a stalled request can't be cancelled). **Every stage is capped, the local read included** (`LOCAL_MS`): reading the on-disk copy can hang too, when persistence is still starting or IndexedDB is wedged, and putting that uncapped call at the *head* of the chain meant nothing downstream could ever time out — a fix that silently did nothing. **Never mutate `src` on an `<img>` that has already painted.** `#viewer img` carries `will-change:transform`, so it is its own compositing layer, and iOS goes on showing the frame it already has — that, not the read, was the long-standing "first photo of an entry stays blurry" bug (the device timed the read at 11ms from disk, 83ms from the server). `vShow()` therefore `paint()`s the first src onto the fresh element — thumbnail, clip, or an already-cached full — and `swap()`s any *second* one: decode off-screen, then `replaceWith` and re-apply the zoom transform, which lived on the old element. A revisit took the paint-once path all along, which is exactly why flipping away and back "fixed" it. `vShow()` ends in a visible state or not at all: it names the failing stage in the retry box (`errCode`), and both call sites catch, because an async `vShow` that throws otherwise vanishes into an unhandled rejection and just leaves the thumbnail up. **Settings → Photo loading** runs `photoSelfTest()`, timing a real read stage by stage (and reporting `S.persist`) — added because this was misdiagnosed twice from the outside. It dedupes concurrent reads and *throws* rather than swallowing a failure; `vShow()` shows a spinner after 180ms (no flicker on a fast read), a tap-to-retry message on failure, and re-checks `vGen` — a monotonic counter bumped by every `vShow()` and by `closeViewer()` — before applying a late response. **Don't go back to comparing the photo object**: the `photos` snapshot swaps those objects out, so identity comparison rejected valid responses *and* skipped the `vBusy(false)` below it, which is what stranded the spinner on the first photo of an entry. `vPrefetch()` warms both neighbours so Prev/Next is instant.
- **External map links** (`extMapLinks`) are for **ideas only** — a single pinned spot you might route to. Memories deliberately have none: their story is the in-app map with both home bases and the route line, which no external map URL can reproduce.
- **Maps:** Leaflet + OpenStreetMap tiles — all keyless/free. Place search: Photon (photon.komoot.io, home-biased) with Nominatim as fallback; reverse geocoding: Nominatim. Never introduce Google Maps (billing).
- **Auth:** Firebase email/password. Two fixed accounts: "Mr. Soccerboy" (partner A, rose) and "Ms. Chairgirl" (partner B, teal). The `PARTNERS` constant in `index.html` holds **SHA-256 hashes** of the two sign-in emails, never the plaintext — identity is derived by hashing the signed-in email (`applyIdentity()`) — and there is intentionally no in-app name/identity editing. **PII policy: the real emails, real names, and personal addresses must never appear in this repo (it's public); they live only in the Firebase console.** If the emails ever change, recompute the hashes.
- **Firestore rules** allowlist exactly the two real emails (see README for the shape, with placeholders). Firebase config in `index.html` is public-safe by design; the rules are the security boundary.

## Data model (Firestore)

- `ideas`: {title, category, desc, when 'YYYY-MM-DD'|null (optional date for time-bound ideas; undated ideas are the norm), until 'YYYY-MM-DD'|null (last day when it runs across several; `ideaEnd()` collapses the pair), loc{name,lat,lng,addr?}|null, notes{A,B}, done{'<item text>':ms}?, created} — dated ideas that haven't passed sort to a **⏳ Coming up** block at the top of the Ideas tab, soonest first, with a relative countdown inside 14 days (a multi-day run currently under way reads “on now”, a single day today reads “today”); an idea stays in that block until its *last* day has passed, after which the date stays on the card, muted. `saveIdea()` normalises the pair: an end alone becomes the date, backwards entry is swapped, a same-day range collapses to one date. `done` records ticked checklist items (see below), keyed by the item's own text — stable across reordering, and `pruneDone()` drops a key on save once its line is gone so a tick can't resurrect if the same text is retyped.
- `dates`: {title, day 'YYYY-MM-DD', refl{A,B}, locs[{name,lat,lng,addr?}...] (`name` is the couple's own label for the stop, renamable in the picker; `addr` is the address it was picked from, shown as secondary text), created, coverId|null (photo doc id shown on the calendar; null = first photo), trash:{by:'A'|'B',at}|null (soft-deleted; hidden everywhere but the Journal's Trash section — only the *other* partner can delete forever, either can restore)}
- `photos`: {dateId, thumb(dataURL), fullId, created, order?, kind?:'clip'} — `kind:'clip'` means `photoFulls.data` holds a silent looping video instead of a JPEG (thumb is its poster frame, `secs` its length) — display order is (order ?? created) ascending; `order` is written 0..n to every photo of a date when the couple rearranges them · `photoFulls`: {data(dataURL)}
- `meta/places`: {'<lat*1e5>_<lng*1e5>': label} — one shared label per physical spot. `placeKey()` rounds to ~1m and uses an underscore because a dot would read as a nested field path. `labelOf(loc)` resolves a spot's name as registry → matching home base label (`homePlaces()`, since dates happen at home) → the loc's own stored `name`, so every list, sheet, popup and map pin shows the same name for a place; `savePlaces()` publishes a rename when an idea or date is saved, and `knownPlaces()/matchPlaces()` back the autocomplete (home bases included, tagged `home` rather than `been here`). Renaming a spot that already has a label asks for confirmation naming both the old and new label; a first-time name does not. **Home bases are named only in Settings** — `savePlaces()` never writes a registry entry at a home's key, `renameLoc()` refuses there, and `saveHome()` deletes any stale registry label at the home's old and new spots, so Settings can always reassert the name. A stop logged at a home stores its **street address** as `name` (never the home label), so if a partner moves, old stops keep their coordinates and fall back to reading as the address. There is deliberately no per-entry override.
- `meta/settings`: {homes:[{label,lat,lng,addr|null}|null ×2]} — created lazily via merge writes; no other settings remain. `addr` is the exact address chosen from search when the home was set (shown in the home picker); when null, the picker falls back to reverse geocoding, which is only approximate.

**Backup** (`makeBackup()`/`saveBackup()`) is deliberately two taps. iOS ignores `<a download>` entirely, so a phone needs `navigator.share({files})` — and that only works from inside a real user gesture, which awaiting the photo reads would spend. So gathering (every `photoFulls` doc, on-disk copy first, capped like the viewer's reads) happens on the first tap and saving on the second, with the anchor path kept as the desktop fallback — appended to the document, since Safari won't click a detached one. The version this replaced clicked a detached anchor and toasted success unconditionally: it never produced a file on a phone, and said it had. Photos that can't be read are counted and shown, never silently omitted. **Settings → Version** also carries a quiet `test photo loading` link; it lives *outside* `#verline`, which `paintVer()` rewrites.

**Data safety:** all user data lives in Firestore, none in this repo. Never write migrations that rewrite existing docs without explicit user sign-off, and remind the user to use Settings → Download backup before schema-touching changes. There is currently no restore-from-backup feature (known gap).

## Code conventions / gotchas

- Rendering is `innerHTML` templates + global `onclick` handlers; `esc()` everything user-authored. `linkify()` turns bare URLs in idea details and notes into links — it escapes **first**, then wraps, never the reverse. Only the *partner's* note renders as HTML (yours is a textarea), so links are clickable in theirs, not your own.
- **Lists in user text** (`richText()`): a line starting with `-`, `*` or `•` is a list item; everything else is a text run (`.rt-p`, which carries the `white-space:pre-wrap` the containers used to). One marker, and **meaning follows the place** — in an *idea's details* items are things you might still do, so they render as tappable checkboxes; in notes and reflections a list is just a list. That's deliberate: a second marker (`v-` and friends) would be a private convention with a typing cost on a phone, and a per-idea toggle would be state to remember to set. Ticking is optimistic (`tickItem()` rewrites `#idea-body` itself, since an open sheet isn't redrawn by snapshots) and writes only the `done` map via `update()`. Ticked items leave the live list for a collapsed **Done (n)** block, newest first — hidden entirely when empty, so a description whose bullets are really logistics still looks normal. Search is unaffected: `desc` stays one plain string, so ticked items are still findable. `splittable()`/`toList()` offer a one-tap "split into list" on the Details field when a line holds middot-separated entries.
- Ideas and the Journal each have a keyword search (`ideaSearch`/`memSearch`), matching every word against title, notes/reflections, category and place label+address. Typing re-renders **only** the list container (`#idea-list`/`#mem-list`) — a full `render()` would rebuild the box and lose focus. A memory search deliberately spans every month, hiding the month pager while active. Because these are the first inputs on the main screen, user-initiated navigation must call `blurActive()` first (see below).
- `render()` skips same-screen re-renders while an input inside `#app` is focused (protects typing from snapshot refreshes) but **must never block screen transitions** — that caused a real login-stall bug on iOS (keychain autofill leaves focus in the password field). The `lastScreen` mechanism handles this; don't regress it. Since the search boxes put inputs on the *main* screen, `setTab`, `setIdeaFilter`, the album/calendar toggles and `goMonth` all `blurActive()` before rendering — otherwise a tap while the search box has focus would silently do nothing.
- `autoGrow()` must collapse a textarea to `height:auto` to measure it, which momentarily shortens the sheet and makes the browser **clamp `.sheet-body`'s scrollTop** — that clamp was a real "view jumps while typing" bug. It saves and restores the position around the measurement, then `caretIntoView()` (via a mirror element in `caretOffset()`) moves the view only if the caret would be off-screen, and only far enough to show it. Resize-only calls pass no `follow` flag so they never move the view.
- The on-screen keyboard covers the page **without changing any element's bounds**, so "visible" is measured against `window.visualViewport` (`viewBounds()`), not the sheet's rectangle. `fitOverlays()` also pins open overlays to the visible area so a sheet's own bottom sits above the keyboard, and `.sheet` uses `max-height:min(94dvh,100%)` so it stays inside that. visualViewport resize/scroll re-checks the caret; `caretAfterKeyboard()` covers focus moves while the keyboard is already up.
- Overlays and the fullscreen viewer freeze the page behind them via a counted `lockScroll()`/`unlockScroll()` that sets `body{position:fixed;top:-scrollY}` — the only thing iOS reliably respects — and restore the offset on close. Deferred work inside a sheet (the `setTimeout` Leaflet draws) must re-check its element exists, since the sheet can close first.
- Clips ping-pong rather than restarting: `playBoomerang()` drives **both** directions by seeking `currentTime` (no browser supports a negative `playbackRate`), advancing by real elapsed time and seeking only when the frame index changes. Playing the forward half natively instead cost a ~100ms stall at the turn while `play()` spun back up. The `<video>` therefore carries neither `loop` nor `autoplay`.
- `[hidden]{display:none!important}` exists because component CSS uses `display:flex` — removing it re-exposes the FAB/tabbar on the login screen.
- Emoji/theming: the user wants **minimal love/heart theming**. The calendar mark on hero screens is a custom `.calico` element showing **JUL 19** (a date meaningful to the user — the 📆 emoji hardcodes July 17, don't swap back). Home-screen icon is `apple-touch-icon.png`, a single date fruit (the pun).
- Journal album is **paged by month**, sharing `S.cal` with the calendar view (so switching views keeps your place). Album arrows (`albumNav`) skip to the next month that *has* memories; the calendar's own arrows (`calNav`) step month by month (empty months in between are worth seeing) but both are clamped: the album to months that have memories, the calendar (`calBounds`) to the oldest memory month through the later of the newest memory month and the current month, so today stays reachable. `initCalMonth()` runs once on first data load so the album doesn't open blank. Trash is listed outside the month filter.
- Test suite resets to one canonical `FIXTURE()` at the start of every section (`resetFixture()`), so a section that mutates state can't silently break later ones — that had happened repeatedly.
- `SEED` array = one-tap import of the couple's original idea list; shown only while the `ideas` collection is empty.

## Testing

No test framework. Verify changes headlessly with Playwright: load `index.html` with CDN scripts stubbed from npm packages (`leaflet`, `firebase` UMD builds), inject state into the global `S` object, assert on DOM, screenshot at 390×844. Firebase network calls can't run in tests — inject state instead of signing in.

## Free-tier numbers (for advice consistency)

Firestore Spark: 1 GiB storage, 50K reads / 20K writes per day. ~3,000 photos of headroom at current compression; clips measure ~100 KB/second stored (~227 KB for a full 3s at 1080p), bounded near 700 KB by `clipBps()`, so clips are cheaper than photos. GitHub Pages requires the repo stay public on the free plan.
